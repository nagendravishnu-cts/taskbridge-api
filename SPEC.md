Notification & Audit Service - Technical Specification

Project: TaskBridge Notification & Audit Service
 Version: 1.0
 Author: Software Engineer
 Date: August 2026

1. Overview

The Notification & Audit Service provides centralized audit logging and user notification capabilities for the TaskBridge platform. The service integrates with the Project Service and is responsible for:

Recording immutable audit entries for project milestone events.
Generating notifications for affected project team members.
Providing query capabilities for audit history.
Tracking notification read status.
Enforcing multi-tenant data isolation and authorization rules.

The service listens to project lifecycle events such as project creation, milestone status updates, and project deletion, ensuring all changes are traceable for compliance and operational visibility.

2. Functional Requirements
2.1 Audit Logging

The system shall:

Record audit events for:
PROJECT_CREATED
PROJECT_UPDATED
MILESTONE_CREATED
MILESTONE_UPDATED
MILESTONE_CLOSED
PROJECT_DELETED
Store previous and new state snapshots.
Capture actor information.
Record event timestamps.
Prevent modification or deletion of audit records after creation.
2.2 Notifications

The system shall:

Generate notifications when project milestone events occur.
Notify all project team members.
Store notification delivery records.
Allow users to retrieve unread notifications.
Allow users to mark notifications as read.
2.3 Audit History Queries

The system shall support:

Query by Project ID.
Filter by event type.
Filter by date range.
Tenant-scoped access control.

4. API Contracts
POST /audit
Purpose

Internal endpoint used by Project Service to record audit events.

Request
{
  "projectId": "proj-123",
  "eventType": "MILESTONE_UPDATED",
  "entityType": "PROJECT",
  "entityId": "proj-123",
  "actorUserId": "user-456",
  "actorOrganizationId": "org-001",
  "previousState": {
    "status": "IN_PROGRESS"
  },
  "newState": {
    "status": "COMPLETED"
  }
}

Response
{
  "success": true,
  "auditId": "audit-789"
}

GET /audit/:projectId
Purpose

Retrieve audit history for a project.

Query Parameters
from=2026-01-01
to=2026-12-31
eventType=MILESTONE_UPDATED

Response
{
  "projectId": "proj-123",
  "records": [
    {
      "eventType": "MILESTONE_UPDATED",
      "timestamp": "2026-08-14T10:30:00Z"
    }
  ]
}

GET /notifications/:userId
Purpose

Retrieve unread notifications.

Response
{
  "notifications": [
    {
      "id": "notif-001",
      "message": "Project milestone updated",
      "isRead": false
    }
  ]
}

PATCH /notifications/:id/read
Purpose

Mark notification as read.

Response
{
  "success": true,
  "message": "Notification marked as read"
}

6. Validation Rules
Audit Validation
projectId must exist.
actorUserId must be valid.
eventType must belong to supported event types.
timestamp is generated by the system.
previousState and newState must be valid JSON.
Notification Validation
recipientUserId must exist.
message cannot be empty.
event type must be valid.
read status defaults to false.
7. Security Requirements
Authentication
All endpoints require authenticated requests.
User identity must be validated before processing.
Authorization
Users may access only data belonging to their organization.
Audit history access must enforce tenant isolation.
Internal audit endpoints are restricted to authorized services.
Data Protection
No sensitive credentials stored in audit records.
Input validation required on all endpoints.
Structured logging must avoid PII exposure.
8. Non-Functional Requirements
Performance
Audit entry creation < 200 ms.
Notification creation performed within transaction scope.
Audit queries support filtering and pagination.
Reliability
Audit entry creation must succeed before transaction completion.
Notifications must be persisted reliably.
Scalability
Repository pattern for database abstraction.
Service layer independent of transport protocol.
Suitable for future event-driven architecture adoption.
9. Constraints
Audit Immutability

Audit entries are immutable.

The service shall:

Allow Create operations.
Allow Read operations.
Reject Update operations.
Reject Delete operations.

Attempting to update or delete an audit event shall return:

{
  "error": "Audit entries are immutable and cannot be modified."
}

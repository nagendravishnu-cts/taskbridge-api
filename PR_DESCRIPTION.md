# Service Integration

## Project Service

Responsible for:

- Project creation
- Status updates
- Project retrieval
- Project deletion

## Notification & Audit Service

Responsible for:

- Audit event persistence
- Notification generation
- Audit history retrieval
- Notification state management

## Integration Contract

Whenever the Project Service processes:

- PROJECT_CREATED
- PROJECT_UPDATED
- MILESTONE_CREATED
- MILESTONE_UPDATED
- MILESTONE_CLOSED
- PROJECT_DELETED

it invokes the Notification & Audit Service to:

1. Persist an immutable audit entry
2. Generate notifications for affected team members

The Project Service acts as the source of truth while the Notification & Audit Service acts as the system of record for compliance and user communication.

# Peer Review Simulation

## Comment 1

**Code Location:** `src/expenses/services/BalanceCalculationService.ts`, `calculateNetBalances()` method, line 45-67

**What Should Change**

The method currently calculates balances assuming all expenses are settled immediately. It should instead track which balances are "pending" vs "confirmed". When a participant disputes an amount, the balance should not be considered final. Add a status field to the SharedExpenseBalance entity with values:

- pending_confirmation
- confirmed
- disputed

**Why (Benefit or Risk)**

In real-world expense splitting applications, users often dispute amounts or add notes before confirming they owe that amount. Without tracking confirmation status, the application may require payment for amounts the user has not accepted, creating both user experience and fraud risks. This also impacts auditability because balance state transitions should be recorded.

---

## Comment 2

**Code Location:** `src/expenses/controllers/ExpenseController.ts`, `createExpense()` endpoint, line 12-34

**What Should Change**

The endpoint accepts participant IDs but does not verify that all participants exist and belong to the same organization. Before creating an expense, validate participants using:

```typescript
await userService.validateParticipantsExist(
  participantIds,
  organisationId
);
```

**Why (Benefit or Risk)**

Allowing expenses to reference non-existent users creates orphaned records and can corrupt balance calculations. It also introduces a security concern because malicious actors could attribute expenses to arbitrary identifiers. Validation improves data integrity and access control.

---

## Comment 3 (AI Blind Spot)

**Code Location:** `src/expenses/services/BalanceCalculationService.ts`, `settleCircularDebt()` method, line 89-125

**What Should Change**

The circular debt detection algorithm assumes all balances use the same currency. Before circular debt analysis, convert balances into a common base currency, perform cycle detection, and convert values back to the original currency during settlement generation.

**Why (Benefit or Risk)**

The current implementation works correctly for single-currency scenarios but can produce incorrect settlement instructions when debts span multiple currencies. This can leave balances unresolved and create inaccurate financial records. Financial systems operating internationally must account for currency conversion during debt reconciliation.

---

# AI Blind Spot Explanation

The issue described in Comment #3 is a domain-specific business logic concern that AI-generated code frequently overlooks. Copilot successfully generated a working circular debt settlement algorithm, but it assumed a single-currency environment because multi-currency reconciliation was not explicitly stated in the prompt.

Human reviewers are better positioned to identify these edge cases because they understand real-world financial workflows, international currency handling, operational risks, and business rules that may not be directly represented in source code. This demonstrates why AI-assisted development still requires human review for complex business domains.
